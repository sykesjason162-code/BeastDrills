Practising In-game The pages WongScript Creating drills

Practising

Beast Drills is spaced repetition for Street Fighter. Each drill is a saved Training Mode setup plus a rule for what counts as success. You practise the ones that are due, the app watches what actually happened, and the ones you keep missing come back sooner.

A session, start to finish

  1. Start from the menu bar (Session → Start Session, or Numpad2). It picks the drill that is most overdue.
  2. A briefing appears first: what the drill is, how it is set up, and what counts as landing it. Start Drill begins; Cancel backs out. Turn briefings off in Session if you already know the deck.
  3. The app applies the whole Training Mode setup for you — dummy behaviour, recordings, reversals, guard, counter state, positions. Every setting the drill does not mention is reset rather than inherited, so nothing bleeds over from the last drill.
  4. Play your reps. The panels get out of the way while a session runs.
  5. When the reps are done, a Drill Complete popup shows how many landed and the grade, with Next Drill, Repeat and Done.
  6. The court is handed back: replay stopped, dummy standing, both players centred. Turn that off in Session → Reset Court When Done if you would rather keep practising the same setup by hand.

Grades and scheduling

Each session ends in one of four grades, exactly like Anki: Again, Hard, Good, Easy. Better grades push the next review further out; Again brings it back tomorrow and resets the streak. You never pick the grade — it comes from what the app observed.

Choosing what is in rotation

Every drill has a tick box, in-game and on the Drills page. The rule is worth knowing because it is not obvious:

  • Nothing ticked — every due drill is in rotation.
  • Anything ticked — only the ticked ones run.

The in-game list says which of the two you are in, above the list.

Difficulty

Every drill can carry a difficulty — very-easy, easy, medium, hard, very-hard — and automatic selection uses it. There is no point being handed a frame-perfect corner route on day one.

  • The two easiest levels are always open.
  • Each next level opens once two drills one level down reach a streak of two. It reuses the streak scheduling already keeps, rather than a second score to grind.
  • Levels open in order, so one lucky hard drill cannot unlock very-hard.
  • A drill with no difficulty is never gated. Unknown is not the same as hard.

This only affects what the app picks for you. Choosing a drill yourself always works — nothing is locked away from someone who deliberately goes and gets it.

Finding a drill

The library is large — over two thousand drills once the SuperCombo import landed — so the Drills page has a real search box rather than a filter. It searches everything, not just what is on screen. Terms are ANDed: every one has to hold.

The in-game Drills menu has a simpler box: a plain substring over the name and id. It is there to reach a drill you can already name, not to run the full query language twice in two languages.

Favorites

The star on a drill card marks it a favorite. Favorites sort to the front of the Drills page — across the whole library, not just whatever page you are on — and favorite:yes finds them in search.

Favorites are also something you can train under: starting a session with Favorites runs only drills you have starred. They still have to be due — a favorite is a shortlist, not a way around scheduling.

This is not the same thing as selection, and the two work together rather than replacing each other:

What it means
SelectedWhat is in rotation right now. Select nothing and everything runs.
FavoriteA lasting shortlist you curate. It only narrows the deck when you deliberately start a Favorites session.

Drills with no character

Most drills name a character. Some do not — anti-airs, parries, hit-confirms, throw tech. Those are fundamentals, and they are scheduled separately for every character you play.

Being able to anti-air as JP says nothing about whether you can anti-air as Ryu, so drilling one does not tick the other off. A fundamental you have never practised as the character you are currently playing counts as new, and comes up straight away — however well another character knows it.

The Drills page reads the same way: while the game is running, badges answer for the character actually loaded. With the game closed there is nobody to answer for, so it falls back to a combined view.

Where the drills came from

Most of the library is imported from the SuperCombo wiki: around two thousand combos across all thirty characters, with each combo's position, damage, difficulty and notes carried across. Frame data for every character is imported alongside it.

Imported drills arrive unticked on purpose. Your own picks keep driving rotation until you deliberately add some — two thousand strangers should not take over your practice.

Not every wiki combo could be translated exactly. Where the notation says something the app cannot state precisely, the combo is skipped rather than approximated: a success rule that is subtly wrong grades Again forever and looks exactly like a broken detector.

When a drill cannot score

Two warnings appear in the panel during a session, and both mean the failure is not yours:

  • "no success criteria" — the drill has no rule for what counts, so every rep grades Again no matter how it is played. Fix it on the Drills page.
  • "empty recording slot(s) for this dummy" — the drill points at a recording slot that has nothing in it for the character you are fighting, so the dummy will just stand there. Recordings are per character.
  • "no checker for: …" — the drill asks for a success category nothing knows how to grade. Same effect as having none, but the cause is a name rather than a blank.

WongScript

WongScript (.wong) is a plain-text way to write drills, one line per setting. It compiles down to the exact same thing the drill form saves -- it's an additional way to edit, not a replacement. Only what you write overrides the defaults; anything you leave out just isn't set.

A full example

title: CH VS DELAYED THROW TECH
description: "Counter on dummy throwing, throw on dummy doing nothing"
position: dummy-corner-right
block: block-after-first-hit
dummy: ryu
reps: 10
game-speed: 5
response-window: 20

wake-up-rev-slot: 0
action: type=common skill=normal-throw, 4f
success: counter-hit, punish-counter-hit

wake-up-rev-slot: 1
action: type=common skill=do-nothing, 0f
success: throw

fixed-success: throw, counter-hit, punish-counter-hit

Two different ways to set what the dummy does

SF6 has two separate systems for controlling the dummy, and WongScript configures them differently:

  • Reversal Options -- one of the dummy's built-in normals/specials/supers/common actions, picked from a menu. WongScript configures this directly: the action: line underneath the slot IS what the dummy does (type= + skill= + delay). This is what the example above uses. SF6's own Reversal Settings screen splits this into three separate 10-slot tabs, each firing at a different moment, and WongScript has a matching key for each:
    • wake-up-rev-slot: -- fires as the dummy gets up from a knockdown.
    • block-rev-slot: -- fires right after the dummy blocks an attack.
    • damage-rev-slot: -- fires right after the dummy gets hit.
    A drill only needs whichever of the three actually matches what it's practicing -- most drills use just one.
  • Recording slots (rec-slot:) -- an actual custom input recording (any sequence of buttons, not limited to the Reversal menu's options), a completely separate SF6 system from Reversal Options. There are two ways to get real content into one: record the dummy's action by hand in Training Mode, then use Save/Override Current Setup as Drill (in-game or the dashboard) to capture that exact recording INTO the drill's own saved data -- from then on, starting the drill automatically writes the recording into the slot and starts it playing, no dependency on that slot still holding the right content in Training Mode later. OR write it directly in WongScript with action: (same keyword Reversal slots use, since it's the same underlying idea -- "what does the dummy do" -- just meaning real FGC motion notation here instead of a built-in move; see the next section), no Training Mode step needed at all for a simple input. The rec-slot: line just activates whichever slot (and its content, from either source) -- if the slot has neither a live Training Mode recording, an embedded one, nor an action: line, the drill reports an unrecorded-slot warning rather than silently doing nothing. Two more things are configurable per drill, matching Recording Settings' own Replay screen exactly: weight: (Random Selection Rate -- when several slots are active at once, higher weight means the game picks that one more often) and the drill-wide repeat-replay: (Off/On/Always Repeat Playback).

Telling these apart in an Anki card comes down to the source wording: "reversal options -> slot N" means the Reversal Options system (use wake-up-rev-slot:/block-rev-slot:/ damage-rev-slot: + action: type=...); "rec -> slot N" means an actual recording (use rec-slot: + optionally action: <motion notation>, a different meaning of the same keyword -- see below). Most real drills so far turned out to be Reversal Options, even ones that looked at first glance like they needed a custom recording.

title: Example Recorded Meaty
position: player-corner-left
reps: 10
repeat-replay: always

rec-slot: 0
action: 236HP, [6:10f], 22LK, [4:4f]
weight: 1
success: perfect-parry

If a slot's action: line is left out, that slot must already have a real recording saved to it in Training Mode or already have one embedded on the drill from a previous capture -- rec-slot:/ weight: alone never create content, only action: does.

Recorded-pattern notation

The dummy's actual input for a Recording slot, written the same way SF6's own combo notation already writes a quick motion input (236P, 623P) -- with one addition: a bracket form for anything that needs an explicit, longer duration (a charge hold in particular), since real notation never states literal frame counts and this has to.

  • Plain step -- a direction (numpad 1-9, 5/N for neutral) or a button (LP/MP/HP/ LK/MK/HK), holds for a fixed 2 frames -- the same quick-input timing a real motion like 236HP already implies. Chain several together with no space to write a real motion: 236HP = down, down-forward, then forward+HP pressed TOGETHER (the LAST direction of any motion always merges with the button right after it, no + needed -- real players press the final direction and the button at the same moment, not one after the other; only earlier directions in the motion, like the 2/3 here, stay their own separate steps). A bare button with no digits (e.g. just HP) is a neutral button press.
  • Held step -- [<code>:<n>f], e.g. [6:10f] (hold forward 10 frames) or [2:5f] (hold down 5 frames, the charge case) -- matches the notation guide's own [X] "hold the input" convention, just with the frame count our own tools need that real notation doesn't track. A charge special composes with the merge rule above for free: [2:5f]8HK = charge down 5 frames, then up+HK pressed together as the release.
  • Simultaneous -- join codes with + inside either form: HP+HK (Drive Impact, both buttons at once, quick) or [6+HP:8f] (hold forward+HP together for 8 frames). Two or more buttons run together with no + at all (HPHK) also count as simultaneous -- it reads the same as HP+HK, just more compact for Drive Impact/Drive Rush. A direction immediately followed by a button, bare, ALSO always means simultaneous now (see Plain step above) -- the only way to keep a direction and a following button genuinely SEQUENTIAL (two separate presses, not one) is to bracket-hold one of them, e.g. [6:2f]HP.
  • Dash / quick reversal -- a direction pressed twice in a row (or through its exact opposite) auto-inserts a real, invisible release between the two presses so it registers as two taps instead of one continuous direction: 66 (forward dash), 44 (backdash), 46, 28, or either diagonal opposite. This applies whether either side is written bare or bracket-held -- [6:2f][6:2f] gets the same release as 66, since the underlying issue (SF6's input buffer blending two direction presses with no real gap between them) doesn't care how the notation was spelled, only whether real release frames actually separate the two presses. No special syntax needed for Drive Rush either -- it's just this plus the simultaneous rule above composed together: 66LPLK at the start of a combo, or bare LPLK mid-combo with no dash needed. There are no exceptions -- a charge release counts too, so [2:45f]8HK reads as "down 45f, neutral, then up+HK together."

Commas mark a real boundary, not just readability. A comma splits the line into separate tokens, and an automatic ~0.1s neutral gap gets inserted between two tokens that are BOTH real moves -- found the hard way: writing a forward hold straight into a quarter-circle motion with no break ([6:20f]236HP, no comma) made the dummy do a completely different special move, because SF6's own input reader looks across the whole recent input stream, and the tail end of the hold plus the start of the motion accidentally spelled out a different real motion. Splitting them with a comma ([6:20f], 236HP) inserts a real invisible neutral gap between them so each motion registers cleanly on its own. The gap is automatic and never shown in the text -- you don't write it yourself. Two exceptions: nothing gets inserted INSIDE one token (the steps of 236HP still have to flow together to register as that one motion), and nothing gets inserted next to a token that's already a neutral pause on its own ([N:12f], a bare N, etc.) -- an explicit pause you wrote yourself already does the same job, at whatever length you chose, so the tool won't stack a second gap on top of it. Your OWN explicit pause always keeps its own visible comma on redisplay too, for the same reason -- it's never regenerable from context the way the two automatic gaps are, so it's never silently swallowed into a neighboring step: 4, N, 6HP, N, 2, N, 8HK always redisplays with every comma intact, never collapsed into one unreadable run. Loading an existing drill's recording as WongScript always shows every step explicitly bracketed with its real frame count rather than compact motion form, since a real captured recording's timing won't reliably match the notation's own 2-frame default -- still exact, just less compact than something typed by hand.

Every line, what it does

LineMeaning
title:The drill's name. Required -- the only line every drill needs.
description:Free text, shown on the drill card.
position:One of dummy-corner-right, dummy-corner-left, player-corner-left, player-corner-right, center, center-reversed.
block:One of no-guard, block-after-first-hit (default), all-block, random-guard.
character:Your (the player's) character -- filters which drills show up for that character's deck. Optional.
dummy:The opponent's character -- used to resolve action: move names below (see next section). Optional, independent of character:.
reps:Attempts per session. Defaults to 10 if left out.
game-speed:0-10 (50%-150% speed), manual override. Leave out for the automatic ramp (slow while you're still learning it, full speed once you've got a streak going).
response-window:Frames of grace before a rep with no response counts as a miss. Leave out for the default.
attempts:slot (the default) counts one attempt each time the dummy's recording or reversal slot plays -- right when the dummy acts and you answer. action counts one each time you do the thing being graded, which is what a hit confirm wants: the recording loops on its own timer and says nothing about how many times you tried. Combo drills ignore this and always count combos. Leave it on slot if any of your success criteria is do_nothing -- an attempt has to be bounded by something that happens, and doing nothing correctly never fires.
wake-up-rev-slot: NOpens Wake-up Reversal slot N (fires on the dummy's wake-up) -- the action:/success: lines right after it belong to this slot, until the next slot line.
block-rev-slot: NOpens Block Reversal slot N (fires right after the dummy blocks). Same action:/success: pattern.
damage-rev-slot: NOpens Reversal After Damage slot N (fires right after the dummy gets hit). Same action:/success: pattern.
rec-slot: NOpens Recording slot N -- the action:/weight:/success: lines right after it belong to this slot, until the next slot line.
weight: NOnly inside a rec-slot: block. Random Selection Rate -- when multiple Recording slots are active at once, the game picks between them weighted by this value. Defaults to 1 (equal odds) if left out.
repeat-replay: off|on|alwaysTop-level, applies to every Recording slot in the drill -- matches Recording Settings' own "Repeat Replay" dropdown exactly. Leave out to keep whatever's already set.
action:Meaning depends on which kind of slot is open. Inside a wake-up-rev-slot:/block-rev-slot:/damage-rev-slot: block: type=<category> skill=<name>, <n>f (see "Action names" below). Inside a rec-slot: block: the dummy's actual input, in FGC motion notation (236HP, [6:10f], etc. -- see "Recorded-pattern notation" above). Optional for a recording slot -- leave out if it already has real content from Training Mode or a previous capture.
success:What YOU need to do for that slot to count as a success. Comma-separated if any one of them counts (e.g. counter-hit, punish-counter-hit), or use > to require things in order — block > hit means block first, then hit. See "Success in order" below.
fixed-success:A top-level override that applies every rep regardless of which slot fired -- for drills where the tool can't tell which slot fired but every outcome grades the same way either way.
combo:Attack-string success for the open slot -- "land THIS move or combo", written in the same motion notation as action: (2MK, HP, 236MP). A single move just has to hit; a multi-move string has to land as a real combo. Matching is a prefix, so extra hits on the end are fine — nobody is ever marked down for carrying a combo further. What the named moves must do is land as an unbroken run, in order: an extra hit between two of them is a different combo, not a longer one, and it does not match. Where a gap is genuinely allowed, say so with .... ... means "anything here": put it at the start to match anywhere rather than from the first hit (for combos whose opener is deliberately unspecified — "any heavy starter > ..."), or in the middle to leave a gap — HP, HP, ..., 236HP requires those two, then anything, then that one.
fixed-combo:The same thing as a top-level override, applied every rep regardless of which slot fired -- the combo: counterpart to fixed-success:.
health: drive: sa:What each player starts every rep with. One number is yours; two, comma-separated, is mine, theirs — the same shape position: uses. Health is a percentage in steps of 10, Drive is 0–6, SA is 0–3. So drive: 0, 6 is burnout practice against a full-meter opponent, and sa: 3 gives you a Level 3 to work with. Leave one out and the game's own default applies (full health, full Drive, no Super) — and it is applied every session, so a burnout drill cannot leave the next drill without Drive.
health-recovery: drive-recovery: sa-recovery:How each gauge behaves after it is set — same mine, theirs shape. refill (the default) brings the value back every rep, which is what makes a drill a drill; standard is match behaviour, so rep two starts wherever rep one left you; fixed locks the gauge and it cannot move at all. You will rarely want anything but the default: health-recovery: standard is for a drill you intend to be able to lose.
cpu-level:Lv 1–8, for a drill whose dummy is set to CPU.
counter:One of standard (default), counter, punish-counter, random. Puts the dummy permanently in that counter-hit state, which is how a punish-counter combo gets practised without needing a recording for it.
require-slot:yes (default) or no. no means the drill's Recording slots are ambient -- the dummy is doing something so you're not hitting a statue, but which slot fired has nothing to do with success. Grading then comes purely from fixed-combo:/fixed-success:.
trains:Comma-separated list of the Against me tally categories this drill is a fix for (e.g. trains: got_thrown, got_hit).{% if scrimmage_available %} Scrimmage ranks what keeps happening to you and recommends the drills that claim it.{% endif %} Optional; unknown category names are rejected rather than silently ignored.
trains-for:The other half, from the What I did tally: the skill this drill builds, rather than the mistake it stops (e.g. trains-for: hit_confirm). Its own vocabulary, so a receiver category like got_thrown is rejected here — a drill cannot train for being thrown. Optional, and a drill may have both, one or neither.
difficulty:One of very-easy, easy, medium, hard, very-hard. Gates automatic selection, so a beginner is not handed a frame-perfect route (see Difficulty). Optional — a drill without one is never gated, because unknown is not the same as hard.

What you can put after success:

Every value the grader understands. A slot can name more than one, comma-separated, and any of them counts.

CriterionCounts as a success when…
anti-airYou hit them while they were airborne. Being airborne has to come first — a hit before the jump does not count.
throwYour throw connected. A real throw, checked on the same frame from both sides, not merely "they took damage".
throw-techYou teched their throw. Getting thrown is the failure.
blockYou blocked their attack.
block-then-punishYou blocked and then punished. In that order — a hit that came first is not a punish.
counter-hitThe hit landed as a Counter Hit — the game's own flag, the one that prints on screen.
punish-counter-hitThe hit landed as a Punish Counter.
perfect-parryYou Perfect Parried. A regular parry does not count. Taking damage does not fail it, because these drills usually need you knocked down first.
reversalYou acted on the first frame you were able to — the REVERSAL the game prints beside COUNTER. Same rule about damage: getting knocked down is how the drill starts.
drive-impactYour Drive Impact landed.
stuff-dashYou hit them out of a dash — the hit has to interrupt the dash, not merely happen nearby.
stuff-drive-rushYou hit them out of a Drive Rush, as a Counter or Punish Counter.
drive-impact-counterYou beat their Drive Impact — hit them while it was still coming out.
drive-impact-vs-diBoth of you Drive Impacted and yours won the clash.
hit-confirmThe opening hit landed and more hits followed — exactly hit > combo. The opener alone is not a confirm: it goes out before you know the answer, so what is being measured is the decision after it. Getting hit mid-combo does not fail it. If you also want to reward keeping your turn on block, add pressure beside it.
pressureThey blocked something of yours and you landed the next one — got-blocked > hit. Keeping your turn, rather than confirming a hit.
do-nothingYou correctly declined to press. Note this one cannot be used with attempts: action — an attempt has to be bounded by something that happens.

Success in order

A comma means any of these. A > means this, and then that — the order you have to do them in for the rep to count.

success: block > hit          block first, THEN hit them
success: hit > combo          the hit landed, THEN more hits followed
success: block > hit > combo  as many steps as you like
success: hit > combo, block > hit    either sequence counts

Order is not guessed after the fact. The mod records the moment each thing first became true during the rep, so block > hit genuinely means the block came first — a rep where you hit them and then blocked is not a punish, and is scored as a miss.

The pieces you can chain, named from your point of view:

What you did: hit, combo, attack, block, parry, perfect-parry, throw, throw-tech, counter-hit, punish-counter (also spelled punish-counter-hit), anti-air, reversal, backroll, wakeup, drive-impact, drive-impact-counter, drive-impact-vs-di, stuff-dash, stuff-drive-rush.
What they did to you: got-hit, got-blocked, got-thrown, got-counter-hit, got-punish-countered, got-drive-impacted, got-anti-aired.

Every criterion in the table above can be chained this way except do-nothing, and that one for a reason rather than an oversight: a sequence asks when each step happened, and nothing happening has no moment.

What you cannot chain is a move. punish-counter-hit > DR > ... reads naturally but asks something different — these are outcomes (what happened to whom), not the buttons you pressed. Which moves you threw is what the combo notation matches, in the combo: field.

Some of the named criteria in the table above are just shorthand for one of these sequences, and the two spellings are interchangeable — write whichever reads better to you:

hit-confirm        =  hit > combo
pressure           =  got-blocked > hit
block-then-punish  =  block > hit

Test drills

A drill whose id starts with debug_ is a test drill: it exists to exercise a detector, not to teach anything. Name one debug_ something and it becomes one. Find them by typing debug_ in the drill search.

They behave differently in exactly two ways, and both are the point. They are never offered automatically — they cannot turn up in a session or count toward a streak — and they are never shipped, so nobody installs somebody else's test rig. Picking one by hand still runs it normally, which is what they are for.

The id is what decides, not the name, and that is deliberate: an id is set once when the drill is created and no edit touches it, so a test drill cannot be renamed into a real one that would then be scheduled and shipped. Each one's description should say what to watch and what a failure would look like, since the whole reason a test drill exists is that the thing it checks cannot be confirmed by reading the code.

Action names -- "type" and "skill"

Every Wake-up Reversal option belongs to one of 5 categories (type=), and within that category it's the Nth move in that category's own list (skill=). These were confirmed directly from the game's own reflection data and from the real in-game Reversal Options menu -- not guessed.

  • type=common -- the one truly universal list, every character shares it: do-nothing, forward, backward, forward-dash, back-dash, vertical-jump, forward-jump, backward-jump, normal-throw, drive-parry, drive-impact.
  • type=normal, type=command-normal, type=special, type=sa -- these are ALL character-specific (even normal -- every character has the same 12 basic normals conceptually, but the list is still captured and stored per-character, not shared), and only resolve to a real name if that character's move list has been captured yet (only Ryu's is captured so far). Set dummy: to the opponent's character to use these. If a name isn't recognized, WongScript will tell you which line is the problem rather than silently guessing wrong.

If a character's list hasn't been captured yet, you can still write the raw numbers directly -- action: type=special skill=2, 0f -- and fix it up later once that character's moves get captured. The dashboard's Form tab does the same thing automatically: pick a Type in a slot's "Dummy's action" section and its Skill dropdown fills in with real names once a dummy: character with a captured list is selected above; without one (or for an uncaptured character) it falls back to a plain skill-index number field.

Dashboard tools

Creating and editing a drill

Click + New Drill (or Edit on an existing one) to open the modal. It has two tabs that both save the same way:

  • Form -- the original point-and-click editor: name, description, position/block dropdowns, character/dummy dropdowns, per-slot chip-based success criteria.
  • WongScript -- editing an existing drill loads its current settings as a script automatically the first time you open this tab (switching back and forth afterward won't re-load it and clobber what you're typing); a brand-new drill starts with an empty script, ready to write from scratch. Just write/edit the text and click Save -- it parses whatever's in the box directly, no separate "fill the form first" step. Errors show inline, with the line number.

Either tab, the actual Save button at the bottom is what commits it -- on the WongScript tab, Save parses the current text first and aborts (showing the real error) if it doesn't parse, rather than silently saving whatever the Form tab happened to hold before.

Use both: build it in the Form, then sharpen it in WongScript

This is how Beast Drills is actually built and how its author works. Jason: "I start the drill in the form, and then add more advanced scripts after it is built from the form. Stops me from having to write a whole script out."

  1. Make the drill in the Form — name, characters, position, slots, the obvious success criteria. Everything you would otherwise be typing out by hand.
  2. Switch to the WongScript tab. Your drill is already there, written out from what you just built — no save needed first, and it works on a brand-new drill you have never saved.
  3. Add the things the form has no widget for — an ordered success: block > hit, a recorded action: pattern, a combo: string.
  4. Click Save.

Switching tabs carries your work across in both directions, and it is only ever held in the page — nothing is written until you press Save, and Cancel throws all of it away, however many times you went back and forth.

Going back to the Form does not reformat script you wrote by hand. The text is only regenerated from the form when you have actually changed something in the form, so you can look at the Form tab and come back without losing your own spacing and wording.

The Form is the easy way in; WongScript is where the advanced settings live. Neither is the "real" one, and you never have to choose — they are two views of the same drill.

Sharing a whole deck

On the Drills page:

  • Export All (.wong) downloads every drill in your database as one text file -- send that file to a friend.
  • Import .wong reads a deck back in -- choose the file, or paste its contents. Each drill starts its own title: line, so one file can hold a whole deck. If some drills in the file have mistakes, the rest still import -- you'll get a summary of what succeeded and what to fix.

Import asks what to do about drills you already have, matched by name:

  • Add only what is new leaves those completely alone. This is the default, and it is the one to use for a pack from a friend when you have drills of your own you don't want touched.
  • Replace them with this file's versions overwrites the drill -- its setup, criteria and combo -- with what the file says.

Your progress is safe either way. Streaks, due dates, favourites and per-character records belong to you rather than to the file, so an import never resets them, even when it replaces a drill outright.

In-game

The menu bar

Everything lives on a bar across the top of the screen. It hides itself until you move the mouse to the very top, and F1 keeps it up permanently. It stays visible while one of its menus is open, so you can reach down into a dropdown without it vanishing.

The panels

The drill list used to be a panel of its own. It is not any more — it lives in the Drills menu, because a floating window holding a list and a start button is a window for the sake of being one. Tick a drill to put it in rotation, click to select it, double-click to start it, and type in the filter box to narrow a long list.

  • Tally — every counter, side by side with its opposite. Available as a panel and as a menu: the menu is for checking between rounds, the panel for watching counts move while you play.
  • Drills — the drill list, as a panel rather than a menu, for leaving open while you work through a session. Numpad5.
    • {% if scrimmage_available %}
  • Scrimmage — the running score and the Won/Lost buttons. Numpad6.

Two more appear only when they have something to say: the briefing before a drill, and Drill Complete after one. While a session is running the panels hide themselves, and the rep count moves to the right-hand end of the menu bar, which is always up.

Criteria Tally

A free-play counter that runs with or without a drill, split into In my favour and Against me — good and bad outcomes for you, rather than who performed the action. Your own whiffed throw counts against you the same as getting hit does. Both sides are tracked left and right so you can see which side you are weaker on. Read it in the Tally menu, or open the panel and watch it move.

Each row pairs a counter with its opposite — parry beside got_parried, hit beside got_hit — because the comparison is the point. A few have no opposite and sit alone: whiff, block_miss, parry_miss and parry_whiff are all your own mistakes with no offensive twin.

Worth knowing what some of the less obvious ones mean:

CounterWhat it is
hit_confirmA combo that did damage
non_hit_confirmThe same string, blocked — you committed and it did not land
hit_high / _mid / _lowWhich height you land at. All mid means you are not opening anyone up
parry_missYou got hit by a strike — a parry you never attempted
parry_whiffYou pressed parry and caught nothing — the opposite mistake
throw_whiffYou missed a throw
throw_missed_meThey missed you with one

Hit zones are recorded separately and always, whether the tally is running or not — that is the lifetime heat map on the dashboard, and it does not need switching on.

Safety

Beast Drills only ever writes to the game in local, offline Training Mode, and it re-checks that every frame rather than once at startup. If the check fails it does nothing at all. The Tally menu shows the gate's current state, so you can see it rather than take it on trust.

The pages

  • Dashboard — what is happening right now: the live session, and the hit-zone heat map for the current matchup.
  • Drills — the whole deck. Create, edit, tick for rotation, import and export.
  • Stats — the Anki-style panels: reviews, forecast, calendar, retention, intervals, ease, hourly breakdown, answer buttons, added.
  • Profile — one character's whole record: drills, due count, success rate, average grade, best streak, their drill mix, their hit zones, and which of their drills need the most work.

Hit zones

A lifetime record of where you get hit, drawn on the character themselves: greyed out, with the zone colours washed over head, body and legs. Hot means most of your damage arrives there.

It is kept per player, dummy and side. An unfought matchup reads as empty rather than borrowing another opponent's numbers — if Ryu and Chun-Li showed the same figures, the map would be telling you nothing.

The line under the nav

Suggestions drawn from your own numbers, in the daftest voice available. It knows what is due, which drills you keep failing, who you never play, and who you keep using as a punching bag.

Mods

Beast Drills is meant to be built on. There are two ways in, and a mod can use either without the other. Everything either one needs is on this page — you never reference our code, and we never reference yours.

What will not break under you

Both surfaces below are versioned, and the version is stated from the first release rather than added when something first breaks. Within a major version, a documented field will not be removed, renamed, or change type; a documented file will not move or change its shape; and a registration file that was valid stays valid.

These can happen at any time and are not breaking changes: new fields appear, new files appear, and there are more characters, drills and counters than there were. Read the fields you know and ignore the rest — if your parser falls over on an unfamiliar key, that is the parser’s bug.

If a major version ever does arrive, api_version goes up and the old shape is documented as gone. Check it and refuse rather than guess.

Reading Beast Drills from another program

Everything Beast Drills knows is written as plain JSON in your data folder — Documents\Beast Drills unless you changed data_dir. Anything that can read a file can read it — another REFramework script, a dashboard of your own, an OBS overlay, a spreadsheet.

The game folder keeps only what ships with Beast Drills: move names, frame data, translations, and beast_drills.ini itself. Your own files are deliberately kept out of there, since mod managers own that folder and some of them empty it when they update a mod.

runtime/live_status.json is rewritten every 30 frames — twice a second — and holds who is playing, whether a session is running, which drill it is, and every tally counter. shared_database.json holds the drills. runtime/inbox.json says what is due next, and its heartbeat is how you tell the service is running at all. stats.db is the long-term history; open it read-only.

Twice a second is not fast enough to animate against, and that is deliberate. A file written sixty times a second costs the player's disk, not ours. So read this for what changes slowly — which drill is running, who is playing, the score so far — and read the game itself for anything per-frame. Your mod has the same access to SF6 that Beast Drills has; if you want the combo counter on the exact frame it moves, take it from the game. What this file is for is the half you cannot get that way: what Beast Drills is currently asking the player to do.

If you are writing in Lua, read this

REFramework sandboxes Lua to reframework/data/, and there is no way out of it. json.load_file refuses absolute paths, io.open is replaced at startup with a version that cannot leave the data directory, and fs.read and fs.glob are rooted there. A Lua mod cannot open Documents\Beast Drills at all.

So the file an overlay actually watches is mirrored into the game folder, where the sandbox is not in the way:

<SF6>/reframework/data/BeastDrills_data/runtime/live_status.json

Only derived state is mirrored, and that is the point: this file is rewritten twice a second, so a mod manager deleting the copy costs nothing. The database and the review history are never mirrored — a second copy of something irreplaceable, sitting in the folder that gets cleared, is a trap rather than a convenience. Read those from data_dir. A C# plugin has no such limit and can read either.

Anything in debug/ is a research dump rather than an interface. They change and disappear without notice, which is what that folder is for.

The folder above is the DEFAULT. beast_drills.ini has a data_dir setting, and somebody running the dashboard on another computer will have pointed it at a network share — so read the setting rather than assuming the path.

What is in runtime/live_status.json:

frame Counts up every frame. Compare it to your last read to tell “the game is running” from “this file is stale”. The file is not deleted when the game closes, so decide for yourself whether it is current — Beast Drills’ own service ignores it past five seconds.
session_status Whether a drill session is running, and its state.
session_attempt_count
session_attempts_target
session_success_count		 Reps done, reps aimed for, reps passed.
tally_enabled, criteria_tally Whether the tally is counting, and every counter with a non-zero value. Counter names get added over time; treat an unfamiliar one as valid.
criteria_tally_side Which side the tally started on, or null. Null is a real value: counts taken with no side belong to neither.
p1_character_id, p2_character_id Who is playing, e.g. "jp". Null until the game says.
p1_combo_cnt, p2_combo_cnt Combo counters. The attacker’s is the useful one — the victim’s stays at 0 through a real combo, which cost this project a long detour to learn.
dummy_slot_id
dummy_reversal_active_slot		 Which recording slot is playing, and which reversal option fired.

Changing something from another program

Never write to shared_database.json or the stats database. They have exactly one writer, and that is what stops two programs racing over your scheduling data and losing a streak. Instead drop one event per file into outbox/; the service picks it up, applies it and deletes the file. Scheduling state and review history are refused from an edit, so a mod cannot cost you practice history however it builds the request.

Putting a mod in this menu bar

Drop a JSON file in BeastDrills_data/mods/ naming what you want in the menu, and it appears — under MODS, or inside FILE or VIEW if that is where a player would look for it. Nothing is compiled together and no code is shared.

mods/frametrap.json

{
  "api_version": 1,
  "name": "Frame Trap Finder",
  "author": "somebody",
  "menu": "MODS",
  "items": [
    { "id": "open", "label": "Open", "hotkey": "F7" },
    { "id": "scan", "label": "Scan current character" }
  ]
}

api_version and items are required; name is what the submenu is called. label is optional — leave it out and the menu shows the real name of whatever the item drives, so there is nothing to keep in step. Write one only to shorten it.

Making an item actually do something

A registration on its own gets you a menu entry, a hotkey and settings. It does not get you behaviour: a click is a file written into mods/_events/ and nothing else. Either watch that folder yourself, or tell us what the item drives and we will do it for you.

keywhat it does
call A Lua global to reach when the item is clicked, dotted — "MyMod.scan". A function is called with the item's args; a boolean is toggled, which is what a menu item means for a flag. The path is walked over the global table and never executed, so naming something can only reach a value that already exists.
checkbox The caption of a checkbox your mod already draws. Beast Drills watches it go past imgui.checkbox, so the tick on the menu is your real state and clicking it sets your real state. Nothing of yours changes.
from Which script file to run once, off screen, to learn that caption's value before the player has opened your UI. Without it the item honestly reads (not seen yet) until you first draw.
window The window this toggle opens. Its close button then switches the toggle off — worth setting, because a mod that calls begin_window(title, true, 0) and discards the result has an X that cannot work.
draw Host your whole interface inside a Beast Drills panel, for a mod with no obvious menu items. While a registration claims it, it draws in one place rather than two — it moves, it does not duplicate.

A local is reachable from nowhere, by anyone. If your state lives in one and you would rather not depend on a caption string, export it — one additive line, no behaviour changed, the same table:

local p1 = make_config()

MyMod = { p1 = p1 }        -- the only line you add
{ "id": "p1", "label": "P1 info", "call": "MyMod.p1.enabled" }

Your draw code reads the field it always read and never learns who set it. This is the robust route; checkbox exists for mods whose author has not done it.

A version we do not read refuses the whole file and says so in the menu, rather than half-registering it, and a file that will not parse is listed with its error rather than skipped — an hour lost to a trailing comma is an hour this page exists to prevent.

Or keep the file inside your own mod

Copying a file into somebody else's folder has a cost you pay later: when a player uninstalls your mod, our menu keeps an entry pointing at nothing. So leave the file where it belongs and name it in beast_drills.ini instead — one line, any name on the left:

[mods]
frame_trap_finder = reframework/autorun/FrameTraps/beast.json

The entry then appears and disappears with your mod, and nothing of yours lives in our folder. Everything else is identical: same format, same events, same hotkeys.

The path is relative to the Street Fighter 6 folder, so it survives moving a Steam library to another drive. A path that resolves outside that folder is ignored — an .ini is a text file somebody might paste into from a forum post. A path whose file is not there is skipped in silence, because that is what an uninstalled mod looks like; anything else wrong with it is reported in the menu, the same as a file in mods/. A name already registered refuses the second one and says so, since two mods sharing a name would share an event filename and one would quietly get the other's clicks.

Settings, in the player's own file

A player hunting for each mod's own settings file is back to the problem beast_drills.ini solved, so declare yours in the same registration file and they appear in theirs:

"settings": [
  { "key": "gap_frames", "default": 3,
    "note": "How wide a gap counts as a frame trap." }
]

Beast Drills adds a section named after your registration, with your notes as comments, the way it generates its own settings. You do not read the ini — the resolved values arrive as a file beside the events you already watch, mods/_settings/<yourmod>.json. A second parser of a format we control means two readers that can disagree about a default, and the disagreement would be silent inside your mod, so you would be debugging our file.

Three promises about that file, because it is the player's: a value they set is never changed, their own comments and ordering survive, and uninstalling your mod does not delete your section — put it back a week later and the settings are still there.

The click arrives as a file of its own:

mods/_events/frametrap_1787900000000.json

{ "mod": "frametrap", "item": "scan", "at": 1787900000 }

Watch that folder, act, and empty the file. The timestamp is milliseconds, zero-padded, so a plain sort is a sort by time.

pcall(fs.write, path, "")   -- consumed

Empty it — do not try to delete it. REFramework strips os.remove from Lua, and fs gives you only glob, read and write, so a Lua mod cannot delete a file at all. os.remove calls nil, a pcall swallows it, and the event stays exactly where it was — to be re-read and re-acted on every time you poll. A toggle wired that way fires several times a second. An empty file does not parse, so nothing acts on it twice; Beast Drills sweeps the empties and clears anything older than a minute, so a mod that is not installed does not collect clicks forever.

That indirection is deliberate: a mod that was not running when the click happened still sees it when it starts.

A mod can claim a hotkey too. One already used by Beast Drills or by another mod is refused, and the reason appears where the shortcut would be, so a key that does nothing is never a mystery. Between two mods the one that sorts first alphabetically keeps it — arbitrary, but stable, where load order would move the binding around. "Num9" and "Numpad9" both work, and a name we cannot read is reported the same way rather than ignored. Bindings only fire while the Beast Drills interface has focus, so a mod hotkey can never leak into the match.

What a mod cannot do

It cannot draw over the game. That needs an ImGui draw list, and those crash SF6 from inside a plugin here — twice, both times taking the game down. A mod draws its own windows through REFramework as it always has.

It cannot reach another mod's locals. If a value lives in a local and no global holds it, nothing can name it — not us, not another mod, not the debug library. That is why checkbox watches a caption instead: the value goes past a function we can wrap even when the variable is out of reach.

And it gets no access to internals — no session object, no scheduler. Everything worth reading is in the files above, which are held still across updates in a way internals are not.
